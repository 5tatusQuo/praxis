# Phase 2 audit: acme coverage snapshot

Date: 2026-11-18 · Client: `acme` (fictional, 20 endpoints) · Snapshot: id 3

**Result: the audit matches the snapshot.** All 6 data-component scores, all 3
rule statuses and the class of all 706 ATT&CK techniques are identical.

## Method

The audit is `docs/audits/audit-client.sh`. It shares no code with the gap
engine: it asks Elasticsearch and Kibana the raw questions with `curl` as the
admin user, applies the rules in `docs/visibility-scoring.md` in `jq`, and
compares the outcome with the latest snapshot from the API. The required
fields per data component were copied into the script by hand from the schema
notes. To repeat it, run on the server:

    docs/audits/audit-client.sh acme 20

Limit: this is an independent scripted derivation written by the same author
as the engine, not a second person's audit. The raw facts in section 1 below
are small enough to check by eye against Kibana.

## What the lab was built to show, and what the snapshot says

| Built into the lab | Expected | Snapshot |

| Process and network events from all 20 hosts, every day | Score 4 | 4 |
| Logon events from 12 of 20 hosts, `source.ip` in half of them | Logon Session Creation 2, User Account Authentication 3 | 2 and 3 |
| Registry events stopped 5 days ago | Score 0, flagged silent | 0, silent |
| No file events at all | File Creation not visible | Not in the component list; techniques that depend on it alone are visibility gaps |
| PRX-000001 and PRX-000002 on process events | Healthy; T1003.001, T1218.011, T1490 and parents covered | 5 covered |
| PRX-000003 on the silent registry source | Blind rule; T1547.001 and T1547 | 2 blind |

The process source shows 25 hosts against 20 expected: 5 extra host names come
from test events replayed during Phases 0 and 1. That is real data in the lab
namespace and the audit counts it the same way.
